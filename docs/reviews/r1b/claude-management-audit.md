# Claude Code independent read-only audit

Concurrent source snapshot; dispositions and actual tests are in MANAGEMENT_ACCEPTANCE.md.

- **Medium — [employees-manager.tsx](/Users/cuifengshan/Desktop/AI-Workforce-OS/web/src/pages/employees-manager.tsx:174), `buildUpdateCommand` / archived-project picker.** Trigger: an employee remains bound to a project that is subsequently archived. The picker renders only `unarchivedProjects` at line 450, so the archived binding remains in `form.projectIds` but has no checkbox through which it can be removed. Every disabled-employee update then validates all retained IDs against `unarchivedProjects` at lines 188–192 and fails—even a name-only update. After disabling an enabled employee, the same dead end prevents cleaning the binding or re-enabling it. Impact: the browser UI cannot manage the employee without bypassing it and calling the API directly. Render selected archived bindings as removable entries, or construct a changed-field DTO that permits explicitly removing stale bindings.

- **Low — [management-commands.ts](/Users/cuifengshan/Desktop/AI-Workforce-OS/src/application/management-commands.ts:236), `requireEmployeeUpdateInput` / `updateEmployee`.** Trigger: submit `employee-update` with only `{ expectedVersion }`. Unlike project updates, employee validation never requires an actual patch field. `EmployeeRepository.update` returns the unchanged snapshot, after which `updateEmployee` still inserts a receipt and immutable `employee-update` audit with identical before/after versions. Impact: a successful API response and permanent audit claim an update occurred when no configuration changed, degrading governance history. Reject employee updates with no mutable fields, consistently with `requireProjectUpdateInput`.

- **Low — [management-commands.ts](/Users/cuifengshan/Desktop/AI-Workforce-OS/src/application/management-commands.ts:585), `mapRepositoryError`, with [projects.ts](/Users/cuifengshan/Desktop/AI-Workforce-OS/src/projects/projects.ts:167), `existingRealDirectory`.** Trigger: create a project with a nonexistent repository path. The validator throws `Invalid repositoryPath: path does not exist`, but the generic `/does not exist/` branch classifies it as `NOT_FOUND`, producing HTTP 404 instead of invalid-request 400. A path whose ancestor is a regular file raises `ENOTDIR`, misses all validation patterns, and becomes a generic 500. Impact: ordinary invalid project-create input is misreported as a missing API resource or server failure, preventing clients from giving corrective path feedback. Classify path-validation errors before repository resource-not-found errors, preferably with typed errors rather than message matching.
