- Medium — Runtime recovery identifies drivers only by mutable string ID. [ports.ts](../../../src/runtime/ports.ts#L62) defines no protocol/version identity, [model.ts](../../../src/execution/model.ts#L10) persists only that ID, and recovery accepts an ID match before constructing the current adapter to parse historical output at [local-orchestrator.ts](../../../src/application/local-orchestrator.ts#L714) and [local-orchestrator.ts](../../../src/application/local-orchestrator.ts#L810). Repro: complete an execution under driver v1 emitting `V1_OK`, stop before reconciliation, then restart with a behaviorally incompatible v2 registered under the same ID. The mismatch guard passes; v2 parses v1’s logs and can incorrectly fail/succeed the task and release occupancy. Persist and compare an immutable driver protocol/capability version before terminal parsing.

- Medium — The configuration-only `runtimes` CLI unnecessarily requires a healthy execution database. [task-commands.ts](../../../src/cli/task-commands.ts#L723) validates and opens `workforce.sqlite`, checks its schema, and constructs repositories before selecting the Runtime catalog at line 730. Repro: retain a valid private `settings.json` but remove, corrupt, or make `workforce.sqlite` schema-incompatible; `workforce runtimes --data-dir DIR` exits with a database error even though the catalog needs only settings and built-in registry metadata. This couples Runtime configuration diagnostics to unrelated storage availability.
